# mdl — Recovery & Refactor Plan

Status snapshot (2026-07-23): builds cleanly (`go build ./...`, `go vet ./...` both clean, go1.23 module on go1.25 toolchain), but `go test ./...` fails — see Phase 0. This is a live-scraper project (site HTML/API shapes drift), so "recovery" here means: get it building/testing green, fix known-broken/unimplemented extractor paths, then pay down structural debt, in that order.

## Phase 0 — Ground truth (do first, no design changes)

1. **`extractor/comic_walker` test panic**: `comic_walker_test.go:44` → `extractor/util/assert.go:34` → dials `stg.yandere.ovh` (a private test-fixture host) which doesn't resolve here. **Decision: replace with snapshot testing.** Remove the remote-host comparison entirely; commit the expected decoded image (or its hash) as a `testdata/*.golden` file under version control and compare against that in `assert.go`. Use a snapshot library (e.g. `github.com/bradleyjkemp/cupaloy` or a hand-rolled `-update` flag that regenerates goldens) so re-baselining after an intentional decode-format change is a one-command, reviewable diff instead of pointing at someone's private server. Apply the same snapshot approach anywhere else in the suite that currently pulls "expected" data from a live/private URL.
2. **`extractor/template/giga_viewer` test failure**: `giga_viewer_test.go:32` — `FindChapter` for `ExtractEpisode` now returns `manga.ErrPaidChapter`. The hardcoded test chapter URL is no longer free to read (real-world content aged out from free tier). Needs a currently-free chapter URL, and the test should skip/mark-inconclusive instead of panicking (`giga_viewer_test.go:34` indexes into an empty slice after the error case).
3. Both test files panic instead of failing cleanly when assertions fail — add `t.Fatal`/early-return after `assert`/`require` checks so one bad case doesn't crash the whole `go test` run and hide other results.
4. Confirm `speed_binb` is NOT dead code — it's imported by `extractor/cmoa` and `extractor/storia_takeshobo` as a shared page-extraction template. Keep it.
5. Decide fate of the two live-network "unit" tests as a class: they're integration tests hitting real, changing production sites. Either tag them (`-tags=integration`, skipped in normal `go test ./...`/CI) or accept they'll periodically bit-rot and need re-golden-ing — but don't let them block a normal build.

**Exit criteria for Phase 0**: `go test ./...` passes or every failure is an explicit, tracked "site changed" issue, not a crash.

4. `downloader/downloader.go` (see Phase 2 for structural issues) — `downloadImages` swallows per-page errors (`log.Error` only, `downloader.go:55-58`), so a chapter with every page 404ing still logs "Download complete". ## Phase 2 — Structural / architecture cleanup

1. **Chapter-concurrency is fake.** `downloader/downloader.go:67-118` (`run()`) creates a semaphore of size 1 around per-chapter goroutines — meaning chapters are always processed strictly sequentially despite the goroutine+semaphore ceremony. Either remove the indirection (a plain `for qi := range d.ch { process(qi) }` loop, no goroutine) or make chapter-level parallelism a real, configured value (new `Application.MaxParallelChapters` alongside the existing `MaxParallelDownloads` for pages).
2. **No cancellation.** Nothing in `downloader`, `extractor/*`, or `cmd/cli/main.go` takes a `context.Context`. Ctrl+C mid-download can't cleanly abort in-flight page downloads; partially-written files stay on disk with no cleanup. Thread `context.Context` from `main()` → `Downloader` → per-page `htt` calls (check what cancellation hooks `github.com/sekiju/htt` exposes; if none, that's an upstream dependency gap worth flagging).
3. **Config struct conflates file-schema with CLI runtime state.** `config/types.go:3-11` — `PrimaryCookie`, `ListChaptersMode`, `DownloadChapters` are pure CLI-flag state living in the same struct that's `koanf`-unmarshaled from `config.hcl`. Split into two types: a `FileConfig` (only `koanf`-tagged fields: `Application`, `Output`, `Sites`) and a `RuntimeFlags`/`CLIArgs` struct populated in `cmd/cli/main.go`'s `parse()`. Keeps the persisted schema honest and avoids surprising round-trip behavior if `config.Params` is ever serialized back out.
4. **`cmd/cli/main.go:63-66`** — the `chapters` subcommand is emulated by manually splicing `os.Args`, rather than proper subcommand flag sets. Low priority, but if a second subcommand is ever added this will get uglier; consider `flag.NewFlagSet` per subcommand dispatched from a `switch os.Args[1]`.
5. **`extractor/extractor.go:43-68`** — `fz[T func() (manga.Extractor, error)]` is a generic function constrained to one concrete func signature — no actual polymorphism gained. Replace with a plain (non-generic) `func withSession(fn func() (manga.Extractor, error)) Factory`.
6. **`extractor/util/assert.go`** test helper calls `t.Error` without `return`, so execution continues into a nil `res`/empty `actual` after failure (masking the real failure with a follow-on panic, as seen in Phase 0 item 1). Add early returns after each `t.Error`, or switch to `require.NoError`.
7. **`getSession` hostname matching** (`extractor/extractor.go:70-78`) is exact-match only — no subdomain/suffix fallback. Fine for now (registry is exact-match too) but document the assumption so a future added site with a variable subdomain doesn't silently fall through to "unsupported website".

## Phase 3 — Consistency & polish (do after 0–2 are stable)

1. Standardize error style across extractors: some return domain errors from `sdk/manga/defs.go` (`ErrChapterNotFound`, `ErrPaidChapter`), others return raw wrapped errors, others panic. Every `FindChapters`/`FindChapter`/`FindChapterPages` implementation should exhaustively use the `manga.Err*` vocabulary — extend `defs.go` with new sentinel errors (e.g. `ErrChapterListingUnsupported`) rather than adding new ad hoc `panic`/`errors.New` calls per extractor.
2. `Page.Decode` being an unexported-looking function field mixed into an otherwise JSON-tagged struct (`sdk/manga/types.go:30-36`) is fine functionally but undocumented — add a one-line comment noting it's intentionally excluded from JSON (no `json:"-"` currently, which is harmless only because nothing marshals `Page` today; add the tag defensively).
3. Update `go.mod` `go 1.23` directive to match the actually-installed `go1.25` toolchain once Phase 0/1 are green, and refresh dependencies (`go get -u ./... && go mod tidy`) in an isolated commit so any breakage is attributable.
4. Re-check `.github/workflows/release-draft.yaml` and `.github/scripts/generate-release-notes.go` still function against current GitHub Actions runner defaults (not reviewed in depth here — do this after code is stable so CI failures aren't noise on top of app bugs).

## Phase 2b — Extractor duplication & fragility (from focused extractor review)

1. **Shared boilerplate**: `New()`, `SetSettings`, `settings *manga.Settings` field are duplicated identically across `cmoa`, `comic_walker`, `corocoro`, `ganma`, `storia_takeshobo`, `giga_viewer` (6x). Extract a shared `base` struct embedding `settings` + `SetSettings` method, embedded by each concrete extractor.
2. **Duplicated `manga.Chapter{...}` construction**: `comic_walker.go` (39-48 vs 101-108) and `ganma.go` (58-65 vs 118-126) build the same struct twice between `FindChapters`/`FindChapter`. Extract a `toChapter(...)` builder used by both.
3. **Cookie-header injection** repeated in `corocoro.go` (x2), `giga_viewer.go:109-111`, `cmoa.go:36` as `if e.settings.Cookie != nil { req.SetHeader("Cookie", *e.settings.Cookie) }`. Wrap in a shared settings-aware request helper.
4. **`speed_binb.go` descramble duplication**: `decode016061` (94-124) and `decode016130` (215-246) do an identical `image.Decode` → `draw.Draw` loop → `png.Encode`, differing only in coordinate generation. Unify into one `descramble(coords []DescrambleCord, w, h int) manga.DecodeFunc`.
5. **`renamer.New(len(x))` + manual page-array loop** repeated in every extractor — extract a shared page-builder helper in `sdk/manga` or `extractor/util`.
6. **`corocoro.go:49,80`**: brittle string-literal matching against JS-escaped JSON embedded in HTML (`"chapterMainName":"`) with no fallback — flag as high-risk-of-silent-breakage, same risk class as the `panic("implement me")` items in Phase 1.
7. **`ganma.go:20`**: hardcoded GraphQL persisted-query `sha256hash` constant — will break silently (opaque unmarshal/empty-result error) the moment ganma.jp rotates it. No detection/versioning. Consider surfacing a clearer error when the query is rejected, and documenting how to re-derive the hash.
8. **`comic_walker.go:135-147`**: XOR "decryption" truncates `keyBytes` to first 16 hex chars with no length validation — add a bounds check so a shorter/longer key fails loudly instead of corrupting output.
9. **`speed_binb.go:41-43`**: `url.Parse` error is swallowed and returns `nil, nil` instead of the error — caller sees empty pages, not a failure. Fix to `return nil, err`.
10. **`extractor/util/assert.go`**: a test-only helper (imports `testing`, `testify`) living in the general `util` package, pulling test dependencies into non-test code. Move to `_test.go` or `internal/testutil`. ## Phase 4 — CI & test infrastructure (from tooling review)

1. **No CI verification exists at all.** The only workflow (`.github/workflows/release-draft.yaml`) is a tag-triggered release job — nothing runs `go build`/`go vet`/`go test`/lint on push or PR. This is the single highest-leverage recovery fix: add a `ci.yaml` that runs `go build ./...`, `go vet ./...`, `golangci-lint run`, and `go test ./...` (with live-network integration tests separated per Phase 0 item 5) on every push/PR to main.
2. **Live-network tests as a systemic pattern**: `comic_walker_test.go`, `bench/main_test.go`, and presumably `storia_takeshobo_test.go`/`giga_viewer_test.go` all hit real production sites/hosts with no mocking. Tag these `integration` (build tag) and exclude from the default `go test ./...` used in CI item 1; keep them runnable manually/on a schedule for site-drift detection.
3. **Zero unit-test coverage** for `downloader/`, `config/`, `internal/renamer/renamer.go` — all pure logic, cheap to test, currently untested. Add basic unit tests once Phase 2 concurrency/config changes land (test the new code, not the old fake-concurrency version).
4. **Dependency notes**: `go.mod` is otherwise healthy (Go 1.23, goquery v1.10, zerolog v1.33, koanf v2 — all current). `github.com/sekiju/htt v0.1.1` is the author's own small single-version HTTP helper — worth deciding whether to keep as an external dep or inline, since it's a single point of failure for the context-cancellation work in Phase 2 item 2 (check what cancellation hooks it exposes, if any). `Masterminds/semver` v1.5.0 (v3 exists) is low-risk but easy to bump during the Phase 3 `go mod tidy` pass.
5. **README** has no "Development" section (build/test commands, architecture overview) — add one once Phase 0/1 land, so the CI setup and project layout are documented for future recovery work.
6. **Adopt Changesets** for versioning/changelog — now implemented with `@changesets/cli` (Node). Each PR adds a small fragment file describing its change + bump type (patch/minor/major); `changeset version` compiles them into `CHANGELOG.md` and bumps the version; `changeset tag` creates the git tag. The CI changeset-check job ensures every PR has a changeset fragment. Replaces the previous `changie` reference and the ad-hoc `generate-release-notes.go` script.

## Phase 5 — Public API & plugin architecture (the actual goal, do last — needs 0-4 stable first)

This is the direction the project was always headed and the reason a clean recovery matters: **`sdk/manga` should become a genuinely public, stable API, and site extractors should become plugins**, not hardcoded imports in `extractor/extractor.go`.

1. **Stabilize `sdk/manga` as the public contract first.** Audit `sdk/manga/defs.go` and `sdk/manga/types.go` for anything that leaks internal/extractor-specific concerns (e.g. site-specific fields bolted onto shared structs). The `Extractor` interface (`FindChapters`/`FindChapter`/`FindChapterPages`/`SetSettings`) is already the right shape for a plugin contract — treat any interface change from here on as a breaking-change event that needs a Changesets major bump.
2. **Replace the exact-match static registry** (`extractor/extractor.go:70-78`, `getSession`) with a **plugin registry**: a `Register(hostPattern string, factory Factory)` call each extractor makes from an `init()` (or explicit registration list), instead of `extractor.go` importing every site package directly. This is the actual mechanism that turns "built-in extractors" into "plugins" — same interface, but the core no longer needs to know concrete package names at compile time.
3. **Decide the plugin boundary**: Go doesn't have a stable in-process plugin ABI across binaries (the stdlib `plugin` package is Linux-only and version-fragile), so pick one deliberately:
   - **In-tree plugins (recommended first step)**: every extractor still ships in the same binary/module, but is decoupled via the `Register()` pattern above — gets you the modular architecture and a stable public `sdk/manga` API without the cross-binary compatibility problem. Third parties can still write their own extractor package against the public SDK and `_ import` it into their own `main`.
   - **True out-of-process plugins (later, optional)**: if isolation/dynamic-loading is actually required, expose the `Extractor` interface over a subprocess RPC boundary (`hashicorp/go-plugin` is the standard Go answer) so plugins can be distributed/updated independently of the core binary. Bigger investment — only pursue if in-tree plugins prove insufficient.
4. **Extract shared extractor boilerplate as part of this, not before**: the `base` struct / `toChapter` helper / cookie-header helper from Phase 2b become part of a small `extractor/plugin` (or `sdk/manga/pluginutil`) support package that third-party extractor authors are expected to use — turns internal de-duplication into public developer ergonomics.
5. **Document the plugin/extension contract**: once `Register()` exists, add a "Writing an extractor" doc (README section or `docs/extractors.md`) showing the minimal shape of a conforming plugin, referencing `sdk/manga` types directly rather than internal ones.
6. **Version `sdk/manga` independently** once it's public (e.g. its own go.mod / module path, or at minimum called out explicitly in Changesets as the versioned public surface, separate from CLI-internal changes) so extractor authors have a stable target to build against.

## Phase 6 — External plugin repositories (future, after Phase 5 lands)

Once `sdk/manga` is stable and `Register()` exists, extractors don't need to live in this repo at all.

1. **Split site extractors out of the core module into their own repos** (one per site, or a shared `mdl-plugins` mono-repo — decide based on how many third parties are expected to contribute vs. how many sites the core team maintains itself). Each plugin repo depends only on the public `sdk/manga` module.
2. **Distribution mechanism**: since true dynamic loading isn't practical in Go (Phase 5 item 3), external plugins are consumed at build time — either (a) a `go.mod` `require` + blank `_ import` in a user's own `main`, or (b) if out-of-process plugins were built in Phase 5, a downloadable plugin binary + manifest the core CLI can discover/load at runtime (subprocess RPC). Pick (a) first; it's zero extra infra and matches the in-tree `Register()` design.
3. **Plugin discovery/registry for users**: a simple manifest (e.g. `plugins.json` hosted in this repo or a docs site) listing known community extractor repos, similar to how many CLI tools maintain an "awesome-x" list before building real package-manager tooling. Don't build a package registry/index service until there's evidence of enough third-party plugins to justify one.
4. **Versioning discipline**: since external plugins pin against `sdk/manga`'s version, any breaking SDK change (Phase 5 item 1) needs a documented migration note — this is where the independent `sdk/manga` versioning from Phase 5 item 6 pays off.
5. **Template/starter repo**: once the plugin contract (Phase 5 item 5 docs) is solid, publish a minimal "extractor template" repo third parties can fork, wired with the shared `pluginutil` helpers and a CI workflow that builds against the current `sdk/manga`.

## Phase 7 — TUI (future, independent of the plugin work)

A terminal UI is an additive, non-breaking feature — it can land any time after Phase 2 (concurrency/context) is solid, since a TUI needs real cancellation and progress signals to be worth building, but it doesn't depend on Phase 5/6 plugin work at all.

1. **Prerequisite**: Phase 2 item 2 (`context.Context` threading) and real progress signals (per-chapter/per-page state, not just log lines) — a TUI without cancellable, observable downloads is just a prettier log viewer.
2. **Library choice**: `bubbletea` + `bubbles`/`lipgloss` (Charm) is the standard modern Go TUI stack — model/update/view architecture fits naturally on top of a `downloader` that already emits structured progress events rather than direct `log.Info` calls.
3. **Decouple `downloader` from direct logging first**: introduce a progress-event interface/channel (`downloader.ProgressReporter` or similar) that both the current CLI logger and a future TUI can consume — this is the actual architectural change the TUI needs; the TUI itself is comparatively thin once this exists.
4. **Scope for v1 TUI**: chapter/page queue view with live progress bars, error surfacing per-item (instead of swallowed per Phase 1 item 4), and a way to cancel a running download cleanly (exercises the Phase 2 context work). Config editing, extractor selection, etc. can come later.
5. **Keep the existing flag-driven CLI mode working** — TUI should be opt-in (e.g. `mdl` with no subcommand/flags launches TUI, explicit flags keep today's scriptable non-interactive behavior) so existing automation/scripts aren't broken.

## Suggested execution order (iterative)

1. Phase 4 item 1 first if possible (add a basic CI build/vet/test workflow) — cheap, and turns every later phase into a verified change instead of an honor system.
2. Phase 0 (get `go test` trustworthy, tag integration tests per Phase 4 item 2) → commit.
3. Phase 1 item-by-item, each as its own small commit (nil-cookie fix, `FindChapters` panics, ganma paid-chapter, stray debug print, update-check hardening) → verify `go build`/`go vet`/`go test` after each.
4. Phase 2 architecture changes, largest first (chapter concurrency, then config split, then context threading) — each is a separable PR-sized change.
5. Phase 2b extractor de-duplication, lowest-risk items first (shared `base`/`toChapter`/cookie-header helpers) before touching the riskier reverse-engineered `speed_binb`/`prototypes.go` code.
6. Phase 3 cleanup and remaining Phase 4 items (unit tests, README, dependency bump, Changesets adoption) once the app is functionally solid again.
7. Phase 5 (public API + plugin registry) only once 0-4 are stable and green — this is a breaking architectural change and should land as its own deliberate, Changesets-tracked major version, not mixed into recovery commits.
8. Phase 6 (external plugin repos) only after Phase 5 has shipped and stabilized in at least one release — don't split extractors out to their own repos against an SDK surface that's still moving.
9. Phase 7 (TUI) can start any time after Phase 2 lands — it doesn't block on or get blocked by Phases 5/6, so it can run in parallel with the plugin work if there's bandwidth for both.

Do not batch Phase 0/1 fixes into one giant commit — each extractor bug is independently verifiable against its own test/site, and iterating in small steps means a site-specific breakage (sites change their HTML often) doesn't block unrelated fixes.
